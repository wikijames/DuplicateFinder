# Synthetic scan performance baseline

The dependency-free benchmark console creates its own temporary fixtures, warms up a tiny scan, measures one workload, validates expected results, and removes only its generated directory. It accepts no source-directory argument and does not scan personal folders. Keep generated fixtures on local storage; do not redirect the temporary directory to personal or shared data. Output is a JSON object without file paths, machine names or exception messages. Errors use type-only messages and nonzero exit codes.

## Run

Build Release, then start a separate process for each scenario. Wait for each process to exit before starting the next. For example:

```powershell
dotnet build DuplicateFinder.slnx -c Release
dotnet tools/DuplicateFinder.Benchmarks/bin/Release/net10.0/DuplicateFinder.Benchmarks.dll small-duplicates standard
dotnet tools/DuplicateFinder.Benchmarks/bin/Release/net10.0/DuplicateFinder.Benchmarks.dll mostly-unique standard
dotnet tools/DuplicateFinder.Benchmarks/bin/Release/net10.0/DuplicateFinder.Benchmarks.dll large-duplicates standard
dotnet tools/DuplicateFinder.Benchmarks/bin/Release/net10.0/DuplicateFinder.Benchmarks.dll cancellation standard
```

Replace `standard` with `smoke` for smaller fixtures. Default scale is smoke. Small workloads contain 200/2,000 files of 4 KiB; duplicate-heavy files share content and unique files use distinct deterministic seeds. Large/cancellation workloads contain three 4/32 MiB files. Fixture generation streams 64 KiB blocks. No packages are added.

## Metrics and boundaries

- Elapsed time covers the core scan, excluding fixture generation, warmup, explicit pre-scan GC and fixture removal. JIT, cache state and background work can still affect it.
- Dataset throughput divides generated bytes by elapsed scan time. It is not physical disk throughput: matching may read files repeatedly, and generated data may be cached.
- Allocated bytes and generation collection counts are process-wide deltas during the scan, including observer/cancellation overhead. They are not retained heap size.
- Peak working set is the process lifetime high-water mark, including warmup and fixture creation. It is not an isolated scan-memory peak or a managed-heap measurement.
- Cancellation is requested by a one-shot timer approximately 1 ms after full hashing starts. Observation latency runs from the timer callback's request to the scan unwinding. Timer scheduling is outside this latency. A run fails validation if cancellation is not observed before completion; retry a larger workload on an exceptionally fast machine.
- Last-reported progress can lag cancelled work due to throttling. Its byte count includes repeated reads and is not an exact final cancelled-work count.

The harness exercises the portable core without Windows identity-provider overhead or the desktop UI. It does not certify end-to-end desktop throughput, cold-cache performance, SSD/HDD differences, all file systems or blocked-storage cancellation latency. Storage class is deliberately not inferred from a drive letter or queried from private machine inventory. Run multiple repetitions on explicitly identified test storage before making release claims.

## Measured buffer change

Baseline smoke runs on .NET 10.0.15 x64 showed 446,539,592 allocated bytes for 200 duplicate 4 KiB files and 210,168,264 bytes for 200 unique files. Hashing previously allocated a fresh 1 MiB buffer on every sample/full pass.

Hashing now rents a reusable 64 KiB buffer and returns it in `finally`, clearing file content even on cancellation/failure. Sampling boundaries, SHA-256, byte verification and cleanup guards remain intact. Concurrency is unchanged. The same smoke workloads allocated 27,060,440 and 462,296 bytes respectively: about 94% and 99.8% less allocation. Timing was variable under local load, so this is an allocation finding, not a speedup claim. Pair-verification buffers and candidate metadata remain allocation targets for future measurements.

Illustrative post-change standard runs (single observations, not comparative speed measurements):

| Workload | Dataset | Scan ms | Allocated bytes | Lifetime peak working set bytes |
| --- | ---: | ---: | ---: | ---: |
| Small duplicates | 2,000 × 4 KiB | 5,427.041 | 271,046,248 | 51,990,528 |
| Unique files | 2,000 × 4 KiB | 1,505.179 | 3,948,112 | 43,307,008 |
| Large duplicates | 3 × 32 MiB | 300.021 | 347,816 | 31,416,320 |

The standard cancellation run observed cancellation in 3.189 ms after the actual request. This does not bound cancellation latency on other storage or during a blocking filesystem call. Background load and fixture teardown were not controlled for this illustrative set; repeat isolated runs before comparing timing.

## Validation and remaining gates

Release build has zero warnings/errors and all 207 tests pass. Five new hash tests compare full and sampled results with framework SHA-256 across zero-byte, 64 KiB and 1 MiB boundaries. All four smoke and standard workloads validated expected matching or cancellation locally. CI runs the three matching smoke workloads without timing thresholds; deterministic cancellation regression tests remain in the test suite. Timer-based cancellation measurement stays local to avoid a scheduler-dependent CI gate. Hosted results remain to be verified.

Physical SSD/HDD comparison, repeated low-memory measurements, desktop identity overhead, persistent opt-in diagnostics, package/license review and the wider release matrix remain open. See the [Windows release checklist](windows-release-checklist.md).
